# 开源方案调研：能不能在别人基础上改

> 日期：2026-09-15
> 方法：GitHub API 分层检索 + 候选仓库状态核实 + 关键源码拉取评估
> 结论口径：星数 / 协议 / 最后推送 均为 API 实测值

---

## 一、结论前置

**没有可以直接 fork 就满足需求的成品仓库。** 原因不是没人做过，而是你的三个硬约束
（绝对离线 / APK ≤ 2.5 MB / 零第三方运行时依赖）恰好把所有成熟项目排除在外：

| 成熟项目 | 为什么不能直接用 |
|---|---|
| `mtotschnig/MyExpenses` ★1180 GPL-3.0 活跃 | repo 320 MB、Room + 架构厚重，砍到 2 MB 比重写还费 |
| `Ivy-Apps/ivy-wallet` ★3175 GPL-3.0 | **已归档**（2026-04 停止维护），Compose + Room |
| `AutoAccountingOrg/AutoAccounting` ★911 GPL-3.0 活跃 | 采集插件而非账本；要 Root/LSPosed；自身联网 |

**但零件很值钱。** 其中最稀缺的两样——两家的**真实列名映射**与**真实通知样本**——都能直接拿到。

## 三、重点：AutoAccounting（★911）

- 仓库：`AutoAccountingOrg/AutoAccounting`，Kotlin，GPL-3.0，主页 ez-book.org
- 活跃度：创建 2024-01，**最后推送 2026-09-14**，1240 个文件
- 定位：基于 Xposed 的**自动化记账模块**；屏幕识别 + 多渠道（应用内 Hook / 通知 / 短信）+
  规则驱动 + AI 辅助
- 三种工作模式：LSPosed（需 Root，最完整）/ LSPatch（需改应用）/ OCR 模式（无障碍 或 Shizuku）

**为什么不能用：**

1. **它是采集插件，不是账本。** README 明说「需要配合专业记账软件使用」，
   目前适配钱迹 / 一羽 / 一木 / 小星——**这些都是联网的商业记账 App**，直接破坏绝对离线
2. **完整能力要 Root + LSPosed**；无 Root 只能退到 OCR 模式，耗电且脆弱
3. **它自身联网**：代码含 `http/api/BillAPI.kt`、`RuleAPI.kt`、`update/RuleUpdateHelper.kt`
   与 AI 辅助模块（README 声称"数据本地化、绝不联网上传"，但存在联网模块——以代码为准）

**它的价值：** 验证了这条数据采集路线真实成立且需求旺盛，并且它的规则体系设计
（6 个规则管理 Fragment + 独立规则提交仓库）值得作为结构参考。

## 四、可直接借鉴的零件清单

### 1. `deb-sig/double-entry-generator`（Apache-2.0，★719）— 价值最高

Go 写的账单转换器，`pkg/provider/{alipay,wechat}/` 下是干净的字段定义：

| 统一字段 | 支付宝 | 微信 |
|---|---|---|
| 时间 | 交易时间 | 付款时间 |
| 商户 | 交易对方 | 交易对方 |
| 商品 | 商品说明 | 商品名称 |
| 金额 | 金额 | 金额 |
| 收支 | 收/支 | 收/支 |
| 方向枚举 | `支出` / `收入` / `不计收支` | `支出` / `收入` / `/` |
| 单号 | 交易订单号 + 商家订单号 | 交易号 + 商家订单号 |
| 状态 | 交易状态 | 交易状态 |
| 账户 | 收/付款方式 | 支付方式 |
| 其他 | 交易分类 | 交易类型、服务费 |

微信交易类型枚举：商户消费、微信红包、转账、二维码收款、扫二维码付款、群收款、退款、
转入零钱通-来自零钱。

> 注意：该项目的输入是 CSV，但**表头名与 xlsx 一致**，可直接作为 `parser_rules.json`
> `importProfiles` 的映射依据。

### 2. `DykiSensei/seamless-bookkeeping`（MIT，★5）— 架构同构 + 真实样本

目录结构与本方案高度一致：

```
notification/  NotificationParser · CategoryClassifier · KeepAliveService
               NotificationListenerHelper · SmsParser · SmsBroadcastReceiver
               accessibility/ AccessibilityCaptureService · AccessibilityExtractor
                              · AccessibilityNodeUtils
```

`NotificationParser.kt` 注释里记录了 6 条**真实通知样本**（调研自 v2ex / AutoAccountingOrg issues）：

- 支付宝收款：`成功收款 1.00 元。享免费提现等更多专属服务...`
- 支付宝付款：`付款成功￥3.00 (AB)湖北武汉黄陂汉口北服装城美宜佳`
- 支付宝支出：`你有一笔 88.00 元的支出，点此查看详情`
- 微信付款：`向 麦当劳 付款 12.30 元`
- 微信收款：`收到 张三 的转账 100.00 元`

**两条实测局限（修正我此前的估计）：**

1. **微信扫码收款自 2020 年后不再发系统通知** → 收款方向的自动覆盖率比估计更低
2. **支付宝转账入账通知不含金额**（`某某给你转了一笔钱，点击查看详细信息`）→ 必须丢弃，不能猜

**可吸收的正则技巧：** `向\s*(?!你|您)(\S+?)\s*付款` —— 用负向断言排除「向你付款」，
干净地区分支出与他人付款。

**但它也有和我一样的疏漏：** 它的金额正则是 `[¥￥]\s*([0-9]+(?:\.[0-9]{1,2})?)`，
**同样漏掉千分位**。本项目修正后的 `[0-9][0-9,]*` 更严，保持自研版本。

### 3. `FridayKoi/WhereIsMyMoney`（Apache-2.0，★3）— 仅可参考逻辑

`util/XLSXParser.kt`（184 行）的表头定位思路可用：扫描行找含「交易时间」的行锁定表头，
列名匹配带 fallback（`findColumn("交易对方", "对方")`）。
**但实现内部是 Apache POI**（`org.apache.poi.ss.usermodel.WorkbookFactory`），
不是轻量方案——只抄逻辑，不抄实现。

### 4. `MickLife/KeepAccounts_v2.0`（★311，单文件 Python）

微信 / 支付宝账单合并与清洗逻辑，可作为编码识别、千分位处理、退款过滤的对照参考。

## 五、协议风险

| 项目 | 协议 | 自用侧载 | 若日后开源分发 |
|---|---|---|---|
| MyExpenses / Ivy Wallet / **AutoAccounting** | GPL-3.0 | 无碍 | **传染**：整个项目须以 GPL 开源 |
| double-entry-generator | Apache-2.0 | 无碍 | 可借鉴，保留声明即可 |
| seamless-bookkeeping | MIT | 无碍 | 几乎无约束 |
| WhereIsMyMoney | Apache-2.0 | 无碍 | 保留声明即可 |

**结论**：自用侧载下 GPL 不构成障碍；若计划开源，**只抄 MIT / Apache-2.0 的项目**，
AutoAccounting 的代码不要抄（它的规则数据可另行评估）。

## 六、采纳策略（不 fork，混合借鉴）

| 层 | 做法 |
|---|---|
| App 骨架 | **保留自研骨架**——它已经满足全部硬约束，改造成熟项目反而更贵 |
| 账单列名映射与枚举 | 抄 `double-entry-generator` → 落进 `parser_rules.json` 的 `importProfiles` |
| 通知样本与正则技巧 | 抄 `seamless-bookkeeping` → 落进 `verify_parser_rules.py` 测试用例 |
| xlsx 读取 | **自研**（系统 `java.util.zip` + 流式 XML，约 300 行）；现成方案要么 10 MB 要么未验证 |
| 规则体系设计 | 参考 AutoAccounting 的规则分层思路（不抄代码） |

**一句话**：这个需求没有「成品可以改」，但有「零件可以抄」——而且零件里恰好包含最缺的
两样东西：**两家的真实列名**与**真实通知样本**。
