## 0. 方案摘要

| 项 | 结论 |
|---|---|
| 产品形态 | 纯本地 Android 记账 App，侧载自用，包名 `com.ledger.offline` |
| 数据获取 | **xlsx 导入为主力与地基，通知监听为日常自动补充，无障碍读屏为可选开关（默认关）** |
| 自动分类 | 三级规则链：用户修正记忆 → 关键词规则（外置 JSON）→ 兜底「未分类」。**不引入 AI 模型**；支付宝「交易分类」列作初始种子（v1.2） |
| 去重与合并回填（v1.2 新增） | xlsx 导入对既有通知记录**先合并、后判重**：按单号/宽松指纹匹配后回填商户名、交易单号、官方分类——既杜绝双记账，又是归类准确率的主要来源（§4.3） |
| 联网边界（v1.1 修订） | **数据永不出户**。双构建版本：`offline` 版零 INTERNET（内核级断网）；`plus` 版声明 INTERNET，但唯一用途是**规则单向下载**（手动触发 + 白名单域名 + 无任何上传代码路径） |
| 规则维护（v1.1 新增） | 规则包托管在 GitHub/Gitee 仓库，`plus` 版在 App 内检查更新、哈希校验、沙盒验证通过后热替换；借鉴 AutoAccounting 的规则更新模式但砍掉其自动后台联网 |
| 体积预算 | APK ≤ 2.5 MB（plus 版 +50~100 KB 网络模块）；三年数据 ≤ 8 MB |
| 数据安全 | 字段级 AES-GCM 加密（密钥由 Android Keystore 托管），索引字段存 HMAC 摘要，不存明文 |

与最初设想的最大差异：**xlsx 导入从「兜底」升为主力**。原因有二——它是唯一 100% 完整且带收款方/收支方向的数据源；且用户已实测确认微信、支付宝导出物均为 xlsx，路径确定可走通。通知监听保留，承担「日常免操作」的实时性价值。

## 1. 需求与边界

### 1.1 做什么

1. 自动获取微信、支付宝的支付记录（金额、收款方、时间、收支方向）
2. 按预设支出类型自动归类，用户可修正，修正结果被永久记忆
3. 流水列表 + 月度汇总 + 分类统计
4. 所有数据本地加密存储，可导出备份
5. 隐私边界（v1.1 修订）：**数据永不出户**——联网（可选开启）仅限规则单向下载，代码层面无任何上传路径、无设备标识、无遥测；`offline` 构建版保留物理断网保证

### 1.2 不做什么（明确的非目标）

| 非目标 | 原因 |
|---|---|
| 上架应用商店 | 自用侧载；商店对通知/无障碍权限审核极严 |
| AI 分类模型 | TFLite 模型 5~30 MB，体积是 App 全部预算的十倍以上，准确率反不如规则+记忆 |
| 云端同步 / 多设备 | **数据出户即违背核心诉求**，与联网放宽无关，仍然禁止 |
| 云端备份用户数据 | 同上；备份只走本地导出文件 |
| 银行卡短信解析 | 覆盖不了微信/支付宝，且权限敏感 |
| 截屏 OCR | 耗电、隐私风险大、准确率差 |
| 预算管理 / 多账本 / 报销 | 超出「记账 + 归类」核心闭环，后续再议 |
| 后台自动联网更新 | 联网必须用户手动触发且界面可见，杜绝任何静默网络行为 |

### 1.3 必须诚实接受的天花板（不是 bug，不要试图"修复"）

- 微信/支付宝的通知**经常不带收款方**，此类记录只能标「未识别商户」，靠长按修正一次后记忆
- 通知监听覆盖率约 70~80%（免密支付、自动续费、银行卡直刷等不产生通知）
- 账目完整性 100% 依赖每月/每季度一次 xlsx 导入补齐，**申请导出这一步本身需要联网**（在 App 之外，由用户手动完成）
- 国产 ROM 会杀后台，需一次性白名单配置

**以上天花板用户已于 2026-09-15 确认接受，作为需求基线的一部分，不再视为待决问题**：①「自动」的上限由微信/支付宝的通知策略决定，是外部约束，非代码可破；②「准确」的兑现路径 = 合并回填（§4.3）+ 修正记忆（§4.4）逐步收敛，而非开箱即 100%。

## 3. 总体架构

### 3.1 数据获取策略（三路）

```
                    ┌─────────────────────────────┐
                    │  微信/支付宝 云端（需联网申请） │   ← 联网环节①，
                    └──────────────┬──────────────┘     发生在 App 之外
                                   │ xlsx 文件
   ═══════════ 手机本地边界 ═══════════
                                   │
   ┌───────────┐  ┌───────────┐  ┌─┴─────────┐
   │ 通知监听    │  │ 无障碍读屏  │  │ xlsx 导入   │
   │（自动·主力）│  │（可选·默认关）│  │（手动·地基） │
   └─────┬─────┘  └─────┬─────┘  └─────┬─────┘
         └──────────────┼──────────────┘
                        ▼
        解析 → 去重 → 归类 → 字段级加密 → SQLite
                        ▲
   ┌────────────────────┴───────────┐
   │ 规则包（JSON，本地可热替换）        │ ← 联网环节②（可选·plus 版专有）：
   └────────────────────────────────┘   手动触发、白名单域名、仅下载规则
```

**联网边界总述（v1.1）**：整个系统只有两个联网环节，①申请账单导出（在微信/支付宝 App 内，用户手动），②规则包下载（在本 App 内，用户手动触发，`offline` 版没有此环节）。**两个环节都是单向获取，没有任何用户数据外发路径。**

三路的定位：

| 通道 | 角色 | 覆盖率 | 用户负担 | 失败模式 |
|---|---|---|---|---|
| **xlsx 导入** | 地基 + 对账基准 | 100%（官方全量） | 每月/每季度手动一次 | 无（解析失败则明示丢弃并计数） |
| **通知监听** | 日常自动 | 70~80% | 一次授权 + 白名单 | 漏通知（由 xlsx 补齐）、无商户名（由记忆补齐） |
| **无障碍读屏** | 可选补漏 | 不确定 | 高（耗电、微信可能风控） | 默认关闭，出问题随时关 |

### 3.2 分层结构（沿用已生成骨架，粗体为本方案修订点）


### 3.3 技术选型约束（不可违背）

1. **零第三方运行时依赖**：仅 androidx.core-ktx / appcompat / recyclerview / constraintlayout。禁止 Room / Hilt / Material Components / **Retrofit / OkHttp** / 任何统计与崩溃 SDK——联网功能用系统自带 `HttpURLConnection` 实现（零体积、零依赖），**绝不为此引入网络库**
2. **联网约束（v1.1 修订）**：采用 **Gradle productFlavors 双版本**——`offline` 版不声明 INTERNET（保留物理断网保证）；`plus` 版声明 INTERNET 但全部网络代码收敛在 `RuleUpdater` 单类中，白名单域名硬编码。两版共享其余全部代码。`offline` 版每次构建后跑 `tools/verify_offline.sh`，`plus` 版跑 `tools/verify_network_safety.py`（检查网络调用点仅存在于 RuleUpdater）

   **落地状态（2026-09-17）**：**构建骨架已实现**，功能未实现，边界如下——
   - 已做：`productFlavors` 两个 flavor（`offline` / `plus`）、`app/src/plus/` 源集目录预留、`BuildConfig.CHANNEL` 与 `NETWORK_ENABLED` 字段、产物与任务名带 flavor、`tools/verify_offline.sh` 改为**按 flavor 分别断言**
   - 未做（属 P3，冻结中）：`net/RuleUpdater.kt`、`app/src/plus/AndroidManifest.xml`（加 INTERNET）、`tools/verify_network_safety.py`、设置页更新入口
   - **关键纪律**：在 RuleUpdater 落地前，**plus 版不得声明 INTERNET**。否则用户装到的是「多要了一个网络权限、却没有任何网络功能」的版本——纯风险、零收益，违反最小权限原则。`verify_offline.sh` 里 `expected_internet()` 对 plus 返回 `no`，P3 解冻时改为 `yes`
   - **两版共用同一 `applicationId` 与签名**：可互相覆盖安装、账本数据不丢；代价是两版不能同时安装（切换即覆盖），这是刻意取舍
3. **解析规则一律外置 JSON**（`filesDir/parser_rules.json` > `assets/parser_rules.json`），微信/支付宝改版后热替换，不重新出包
4. **不引入 Apache POI**：10 MB 级 JVM 库，Android 上既超体积又跑不动；xlsx 用系统自带 `java.util.zip` + XML 解析器实现
5. **字段级加密，不用 SQLCipher**：省 2~3 MB native .so
6. **解析宁缺毋滥**：金额解析不出、收支方向判不出 → 直接丢弃并计数，不猜默认值。错误的账目比缺失的账目更糟
7. **无任何上传路径（v1.1 新增）**：代码审查红线——不出现任何 POST/PUT 请求、不采集设备标识（Android ID / IMEI / 序列号）、不写任何遥测埋点。`verify_network_safety.py` 以静态扫描兜底

## 4. 核心设计

### 4.1 xlsx 解析层（本方案唯一全新模块）

xlsx = zip 容器 + 若干 XML。最小读取器只需三个部件：

| 部件 | 作用 | 实现 |
|---|---|---|
| 容器解包 | 读取 zip 内指定条目 | 系统自带 `java.util.zip.ZipInputStream` |
| 共享字符串表 | `xl/sharedStrings.xml` → 字符串数组 | 系统 XML 流式解析 |
| 工作表 | `xl/worksheets/sheet1.xml` → 行/单元格流 | 同上 |

实现要点：

- **流式解析**，不把整个 XML 载入内存（年度账单可达数万行）
- 单元格类型处理：`s`（共享字符串索引）、`inlineStr`、`n`（数字）；按 `r` 属性（如 `B5`）定位列，容忍空单元格
- **表头自动定位**：微信/支付宝的 xlsx 开头有若干行说明文字，真实表头在中间。扫描前 N 行，命中表头特征词（如「交易时间」「交易对方」「收/支」）即锁定表头行
- **来源识别**：按表头特征区分微信 vs 支付宝（两家列名不同），映射关系外置到 `parser_rules.json` 的 `importProfiles`
- **按表头名取列**，绝不按列号硬编码（对方改版调列序不会炸）

关键映射（字段名以真实文件校准）：

| 统一字段 | 微信 xlsx | 支付宝 xlsx |
|---|---|---|
| 时间 | 交易时间 | 交易创建时间 / 付款时间 |
| 商户 | 交易对方 | 交易对方 |
| 金额 | 金额(元) | 金额（元） |
| 收支方向 | 收/支 | 收/支 |
| 交易单号 | 交易单号 | 交易号 |
| 状态过滤 | 当前状态 | 交易状态 |
| 支付方式 | 支付方式 | （收/支 栏之外的账户信息） |

过滤规则：

- 仅导入「交易成功」状态的记录
- 丢弃「不计收支 / 中性交易」（零钱转入转出、信用卡还款等内部资金移动）
- 丢弃「已全额退款」；部分退款在备注体现，不单独建模
- 金额列含千分位逗号（`1,299.00`），解析前去逗号（此缺陷已在通知解析侧修复过，xlsx 侧沿用同一清洗函数）

### 4.2 通知解析层（已有，保留）

- `NotificationCaptureService`：包名早筛（仅微信/支付宝）+ 10 秒签名短路
- `TransactionParser`：金额正则 `[0-9][0-9,]*`（千分位已修复）、方向关键词表、`NOISE_MERCHANTS` 商户黑名单、`STOP_WORDS` 截断
- 解析不出金额或方向 → 丢弃（宁缺毋滥原则）
- 已用 `tools/verify_parser_rules.py` 验证 9/9（含 3 个负例）

> **P1 修订（2026-09-17）**
>
> 1. **落库改走融合**：通知与无障碍现在都走 `ServiceLocator.persist()`，而它内部调用的是 `mergeOrInsert` 而非 `insert`。
>    早先只有账单导入走融合，通知走直插——那个设计在「先通知后账单」的顺序下没问题，
>    但在 P1 的真实用法（先补录历史账单，再日常收通知）下会让同一笔记两遍，详见 §4.3。
>    `persistRecord()` 这条「绕过融合直接插」的公开捷径已删除：只要它还开着，迟早有调用点图省事走上去。
> 2. **服务存活心跳**：系统**没有**「监听服务此刻是否活着」的查询接口，
>    `NotificationManagerCompat.getEnabledListenerPackages()` 只回答「授权过没有」，而这个授权是持久的——
>    服务被 ROM 清掉之后它照样返回 `true`。于是 App 显示「已开启」、实际一笔没记，是最隐蔽的失效方式。
>    对策：服务在 `onListenerConnected`（连上总线）与「包名命中的通知到达」两处写心跳（`capture/CaptureStatus.kt`），
>    界面据此区分「已授权且在跑」「已授权但服务没起来」，后者显式告警 + 引导到后台白名单。
>    心跳只在**解析之前**记录——要的是「通道活着」的证据，与「规则还够用」无关。
> 3. **后台白名单引导**：自启动管理页是厂商私有实现、无统一 Action，
>    故按候选清单逐个 `resolveActivity` 再跳转（小米/华为/OPPO/vivo/一加/三星等），
>    全部失败则退到 AOSP 标准的应用详情页——保证任何机型上点了都有反馈，不做「猜中才有用」。
> 4. **开机提醒不再说「已恢复运行」**：接收器只知道「开机了」，无法确认服务是否被系统绑上，说死即是骗用户。
>    现在改为中性提示 + 点击进入 App 查看采集状态；未授权时干脆不发（避免变成关不掉的噪声通知）。

### 4.3 去重与合并回填（v1.2 核心修订，原「去重（双路）」）

同一笔交易会同时被「通知」和「xlsx」捕获。v1.1 只做判重丢弃，存在审计确认的缺陷：**通知记录经常缺商户名（空或「未识别商户」），与 xlsx 记录的真实商户名指纹对不上 → 判重失败 → 同一笔交易双记账**。v1.2 改为「先合并、后判重」。

**xlsx 记录入库时的匹配顺序（逐条执行）：**

| 序 | 匹配规则 | 命中后动作 |
|---|---|---|
| 1 | 交易单号精确匹配（`txn_no`） | **合并回填**，不新插入 |
| 2 | 宽松指纹：`金额 + 方向 + ±3 分钟时间窗`（仅当既有记录来自通知且商户为空/未识别） | **合并回填** |
| 3 | 完整指纹：`金额 + 商户 + 方向 + ±3 分钟`（双方都有商户名） | 丢弃 xlsx 副本，保留原记录 |
| 4 | 全部未命中 | 作为新记录插入 |

反向场景（xlsx 先入库、通知后到）同样处理：通知记录命中既有单号/指纹 → 直接丢弃通知副本（通知是信息量少的一方，永远不覆盖 xlsx）。

> **反向场景的实现修订（2026-09-17，P1）**
>
> 上面这条「反向场景」在 P0 只写进了文档，**代码里并没有实现**——直到 P1 审计才发现。
> 原因是一个不对称：L2 宽松指纹原本的判据是「**既有记录**缺商户名且来自通知」
> （`c.merchantUnknown && c.fromNotification`），只覆盖「通知先落库、账单后到」；
> 而反向时缺商户名的是**新来的那条通知**，既有账单记录有商户名，
> 两边 `merchant_hash` 永远对不上 → 判定为新增 → 同一笔记两遍。
>
> 修法：把判据改成「**至少有一方是通知来源，且该方没有商户名**」，两个方向共用同一扇门。
> 守住的边界不变——两边都有单号且不一致时仍禁止指纹合并（那可证明是两笔不同订单）。
> 命中的如果是通知（信息量少的那方），`backfillPlan` 自然返回空 → 调用方判为重复丢弃，不回填任何字段。
>
> 影响面：这是「先补录历史账单、之后日常收通知」这一 P1 典型用法下的**必然重复记账**，
> 不是概率问题。新增 6 个单测覆盖反向方向（含「通知自己带商户名时不开宽松门」等负例），
> `MergeMatcherTest` 由 18 个用例增至 24 个。

**合并回填的内容**——xlsx 是唯一自带商户名的数据源，回填直接决定归类准确率：

| 回填字段 | 来源 | 作用 |
|---|---|---|
| 商户名 | xlsx「交易对方」 | 「未识别商户」记录获得可归类主体 |
| 交易单号 | xlsx 交易号 | 此后按单号精确判重，永不再重 |
| 官方分类 | 支付宝「交易分类」 | 分类种子（§4.4） |
| 对账标记 | — | 标记「已对账」，统计页可区分账目完整区段 |

实现约束：
- 指纹存 HMAC 摘要（`amount_hash` / `merchant_hash`），不解密也能查
- 回填只补空字段，**永不覆盖用户已修正的分类**（修正记忆优先级最高，不可被任何自动逻辑推翻）
- 该逻辑在 P0 实现，用单测构造「通知先入库 + xlsx 后导入」的重叠数据验证；P1 真机复验

> **实现状态（2026-09-17，已落地）**
>
> | 位置 | 实现 |
> |---|---|
> | `data/MergeMatcher.kt` | 四级判定 + 回填计划，**纯 Kotlin 无 Android API**，可在纯 JVM 单测 |
> | `data/TransactionDao.kt` | `mergeOrInsert()`：先匹配后写入；`loadCandidates()` 走 `idx_txn_match(amount_hash, direction, occurred_at)` |
> | `data/LedgerDb.kt` | v3 非破坏性迁移，仅新增匹配索引，不动数据 |
> | `capture/BillImporter.kt` | 导入改走 `mergeRecord`，导入结果单列「合并回填 N 笔」 |
>
> 实现时相对原设计**收紧了一处**：官方分类只允许替换**兜底分类**（`classify_rules.json` 的 `fallback`）。
> 原设计写的是「回填官方分类」，但 §4.4 定的优先级是 **用户记忆 > 关键词规则 > 官方种子 > 兜底**——
> 若既有记录的分类是关键词规则命中（如 `entertainment`），官方种子**不许**覆盖它。
> 为落实这条，`Classifier.Classification` 增加 `fromSeed` 字段**如实回报分类来源**，
> 回填据此判断，而不是只看「账单里有没有分类列」。
>
> 另一个守卫：**两边都有交易单号且不一致时禁止指纹合并**——这是可以证明的两笔不同订单，
> 若被合并就是丢账（同金额 + 同方向 + 三分钟内的高频场景）。

### 4.4 分类引擎（三级，全部本地）

```
商户名归一化（去分店/城市后缀）→
  ① 用户修正记忆（merchant_override 表，优先级最高，永久生效）
  ② 关键词规则（classify_rules.json，按关键词长度决胜，避免「星巴克臻选」输给「星」）
  ③ 兜底「未分类」
```

- 预设分类：餐饮、交通、购物、居住、医疗、娱乐、转账、红包、教育、其他（可编辑）
- **修正记忆是准确率的核心来源**：用户长按改一次分类 → 写入 `merchant_override` → 同类交易永久自动命中。用得越久越准
- **支付宝「交易分类」列作初始分类种子（v1.2 修订）**：支付宝导出自带真实分类（餐饮/交通等），导入及合并回填时直接映射到预设类别，初始未分类率大幅下降。微信的「交易类型」（商户消费/转账/红包）**不是**支出类别，仅作辅助信号——两家区别对待，不混用
- 官方分类是种子不是终裁：优先级仍低于用户修正记忆与关键词规则命中（官方分类粒度粗，如「日用百货」vs 用户自定义的「母婴用品」）

### 4.5 存储与加密

| 设计 | 决策 |
|---|---|
| 数据库 | 系统自带 SQLite（零依赖） |
| 加密粒度 | 字段级 AES-GCM，密钥由 Android Keystore 托管（密钥不出安全硬件） |
| 加密字段 | 金额、商户名、备注 |
| 索引字段 | HMAC 摘要（`amount_hash` / `merchant_hash`），支持去重与查询，不解密 |
| 密文存储 | **二进制 BLOB**，禁止 Base64（否则多膨胀 33%） |
| 时间/分类/来源 | 明文（统计需要，敏感度低） |

### 4.6 规则热替换

- 加载优先级：`filesDir/parser_rules.json` > `assets/parser_rules.json`
- 修改固定流程：改 JSON → 跑 `python tools/verify_parser_rules.py` → 通过后再同步 Kotlin 与单测 → `./gradlew :app:testDebugUnitTest`

### 4.7 规则在线更新（v1.1 新增，仅 plus 版）

**动机**：v1.0 中规则热替换虽然不用重新出包，但更新规则仍需「电脑改 JSON → adb push / 文件管理器放入 filesDir」，摩擦大。微信/支付宝改版后解析失效的窗口期内，通知采集等于停摆。参考 AutoAccounting 的 RuleUpdateHelper / AutoRuleSubmit 模式（该项目的规则由社区经 GitHub Issue 提交、App 内检查更新），吸收其「规则与代码分离、云端维护」的思路，但**砍掉它的自动后台更新**——所有联网动作必须是用户手动触发、界面可见。

**规则包格式**（托管在 Git 仓库，GitHub 主源 + Gitee 镜像二选一）：

```
rules/
  manifest.json          # 版本号 + 各文件 SHA-256 + 兼容的 App 最低版本
  parser_rules.json      # 通知解析 + xlsx importProfiles
  classify_rules.json    # 关键词分类规则
  samples_positive.json  # 必须解析成功的样本（含 double-entry-generator
  samples_negative.json  # 与 seamless-bookkeeping 的真实样本）
```

**更新流水线（五道闸门，任何一道失败即放弃、保留原规则）**：

```
手动点「检查更新」
  → ① GET manifest.json（域名白名单校验，非白名单 host 直接拒绝）
  → ② 比对版本号，无新版本则结束
  → ③ 下载规则文件 → SHA-256 校验
  → ④ 沙盒验证：用内置校验器跑 samples_positive/negative，
       新规则必须全样本通过（宁缺毋滥原则同样适用于规则本身）
  → ⑤ 通过后原子替换 filesDir 规则；失败则保留原规则并明示原因
```

**网络面收窄的工程保证**：

| 手段 | 说明 |
|---|---|
| 唯一出口类 | 全部网络代码收敛在 `net/RuleUpdater.kt` 单文件（约 200 行），其余代码零网络调用，静态可审计 |
| 域名白名单硬编码 | `raw.githubusercontent.com` / `gitee.com`，host 不匹配即拒绝连接 |
| 只 GET 不 POST | 请求无参数、无设备标识、无 cookie；服务端无法从请求中获知任何用户信息 |
| 禁明文流量 | `network_security_config` 中 `cleartextTrafficPermitted="false"` |
| 手动触发 | 设置页显式按钮，无 WorkManager/定时任务/开机自动检查 |

**规则源内容来源**：初始规则直接吸收开源调研的成果——double-entry-generator 的两家列名映射与收支/交易类型枚举、seamless-bookkeeping 的 6 条真实通知样本与负向断言正则。日后微信/支付宝改版，改仓库里的 JSON 即可，App 内一键更新。

**offline 版兼容性**：`RuleUpdater` 类在 offline flavor 中不编译入包（sourceSet 隔离），设置页也不显示更新入口；offline 版更新规则仍走 v1.0 的本地热替换路径。

## 5. 隐私与安全（v1.1 修订）

| 措施 | 说明 |
|---|---|
| 数据永不出户 | 联网仅限规则下载（单向 GET）；代码无 POST、无设备标识、无遥测，静态扫描兜底 |
| offline 版物理断网 | 不声明 INTERNET，内核级无法创建 socket；担心任何风险时装这一版 |
| 构建后验证 | `tools/verify_offline.sh` 对**两个 flavor 的所有 APK** 逐个用 aapt 直读权限并分别断言（offline 必须无 INTERNET；plus 在 P3 前同样无）；P3 解冻后 plus 版另跑 `tools/verify_network_safety.py`（网络调用点仅存在于 RuleUpdater + 权限清单核对 + 体积报告） |
| 字段级加密 | 敏感列 AES-GCM；Keystore 托管密钥 |
| 不导出组件 | 无 exported Activity/Provider；关 `usesCleartextTraffic`；`data_extraction_rules` 禁云备份 |
| 权限最小化 | offline 版 4 项 / plus 版 5 项（见 §7） |
| 诚实告知 | 通知使用权是**全量**的（系统不提供按 App 过滤），代码只处理两个包名，但权限覆盖全部通知。v1.0 靠零 INTERNET 对冲；v1.1 的对冲变为「plus 版无上传路径 + offline 版物理断网」，**担心通知内容泄露时改装 offline 版即可** |
| 规则包防投毒 | HTTPS + manifest 内 SHA-256 + 沙盒全样本验证，三重闸门后才替换生效 |
