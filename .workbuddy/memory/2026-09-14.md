# 2026-09-14

## 交付：总体设计方案 v1.0

用户要求「结合以上探讨结果，设计一套全面可行的方案」→ 产出 `docs/方案设计.md`（方案讨论稿，待拍板）。

### 方案核心决策
1. **xlsx 导入从兜底升为主力与地基**——唯一 100% 完整且带收款方/收支方向的数据源，
   且用户已实测两家导出物均为 xlsx。通知监听降为日常自动补充，无障碍保持可选默认关
2. **P0 改为导入闭环先行**（原计划通知监听先行）——xlsx 路径确定性最高，
   可先跑出可用的纯导入型 App，通知采集后续叠加
3. 新增模块：`parse/xlsx/XlsxReader.kt`（系统 zip + 流式 XML，零新依赖，禁 POI）、
   `capture/CsvIo.kt` → 改造为 `BillImporter`（来源识别 + 表头自动定位）
4. 明确非目标清单：不上架、不做 AI 模型、不做云同步、不解析短信、不做 OCR
5. 体积预算锁定 APK ≤ 2.5 MB（保 appcompat；纯平台可到 0.6~1.0 MB 列为开放问题）
6. 密文以 BLOB 存储，禁 Base64（+33% 膨胀）

### 待用户拍板（方案 §11）
1. 体积取舍：保 appcompat（2.5MB）vs 纯平台（1MB）
2. 微信服务号通道 xlsx 能否保存到手机文件夹（决定导入是否纯手机闭环）
3. 用户通知是否带商户名（决定自动分类上限）
4. 是否做本地备份导出（建议做，P3）
