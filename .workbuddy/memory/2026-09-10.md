## 已交付：Android 工程骨架（OfflineLedger）

41 个文件，约 2300 行。包名 `com.ledger.offline`，minSdk 26 / targetSdk 34。

### 分层结构
```
capture/   NotificationCaptureService（主力）· ScreenReadService（补充，有节流闸门）
           BootReceiver · CsvIo（导入导出）
parse/     TransactionParser（宁缺毋滥）· RuleStore（assets → filesDir 热替换）
classify/  MerchantNormalizer · Classifier（记忆 > 关键词长度决胜 > fallback）
data/      LedgerDb · TransactionDao（±3min 时间窗去重 + txnNo 去重）
crypto/    FieldCipher（Keystore AES-GCM 字段级加密 + HMAC 索引摘要）
core/      ServiceLocator（手工 DI，不用 Hilt）
ui/        MainActivity · TransactionAdapter
```

### 关键工程决策
1. **零第三方运行时依赖**（不用 Room / Hilt / Material / 任何统计 SDK）→ 保证无隐式 INTERNET 权限 + 体积
2. **字段级加密而非 SQLCipher** → 省掉 2~3 MB native .so；merchant_hash / amount_hash 用 HMAC 做可查询索引
3. **规则全部外置 JSON**（parser_rules.json / classify_rules.json）→ 微信支付宝改版后可离线热替换
4. **不做 AI 分类** → TFLite 模型 5~30 MB 是负收益，规则 + 用户修正记忆准确率更高
5. **去重是刚需** → 通知与无障碍会捕获同一笔，用 ±3min 时间窗 + 金额 + 商户指纹

### 已修复的真实缺陷（由 tools/verify_parser_rules.py 发现）
- 千分位金额 `¥1,299.00` 被正则截断成 1.0 → 金额正则改为 `[0-9][0-9,]*`
- 正则会把「微信支付」「支付宝」当成商户名 → 增加 NOISE_MERCHANTS 黑名单 + STOP_WORDS 截断

### 验证状态

- ✅ 3 个单元测试文件（Parser / Classifier / CsvIo），纯 JVM 不依赖 Android

## 关键事实核查：账单文件到底在哪（2026-09-10 查证）

用户反问："我也没有 csv 文件导入啊，微信支付宝支付记录有 csv 存在哪？"
—— 这个反问直接动摇了上一轮把「方案 B 纯 CSV 导入」评为性价比最优的结论。

### 核实结果
1. **手机上不存在现成的账单文件**。微信官方文档原话：微信支付账单存储在腾讯云端服务器，
   不在手机本地，删除的只是本地显示 → CSV 是「申请后才由云端生成并投递」的产物。
2. **微信有两条投递渠道（官方文档 pay.weixin.qq.com/doc/user/4021834826）**：
   - 接收方式=微信：「微信支付」服务号下发，**可直接打开，无需解压码**，下发后 7 天内有效
   - 接收方式=邮箱：加密 zip 到邮箱，6 位解压码通过服务号下发；无下载有效期
   - 用途两种：用于个人对账（Excel）/ 用作证明材料（PDF 盖章）；24 小时内下发；需刷脸或支付密码
   - 存在冲突说法：部分内容站称「只能发邮箱、不能在微信里下载」→ 疑似版本差异，必须实测
3. **支付宝**：我的 → 账单 → ··· → 开具交易流水证明 → 用于个人对账（xlsx 无章）/
   用于材料证明（PDF 带电子章 + 邮箱加密 zip，解压码=身份证后 6 位）。
   "APP 内直接生成 xlsx 保存到手机、无需邮箱"这一说法**只有内容站支撑、无官方文档**，标记为待验证。

### 对方案评价的修正
- 方案 B 不是"拿一个现成文件"，而是"每次跑一遍申请流程"；且**申请环节天然要联网**
  （App 本身仍可零 INTERNET，但数据获取环节在 App 之外，账单要经过腾讯/阿里服务器 + 邮箱服务商）
  → 与"绝对离线、隐私安全"的初衷存在张力，需向用户明示
- 若微信「服务号」渠道可用 → B 能在手机端闭环，从"8 步 + 电脑"降级为"手机里几步"
- **方案 D（无障碍读账单列表页）上一轮判得太死**：账单列表是标准列表 UI，
  理论上可读，且同时满足"实时 + 完整 + 无需导出"，应重新评估
- 官方自有「微信记账本」小程序 / 支付宝记账本，已自动同步各自账单并自动分类
  → 本项目的差异化只剩：跨平台合并 + 本地不上云 + 分类规则自定

## 实测结论（2026-09-11 用户确认）

**微信与支付宝导出的账单均为 .xlsx**（不是 csv）。
→ `CsvIo` 无法直接吃这个文件，必须新增 xlsx 解析层。

### xlsx 解析方案（已定）
- xlsx = zip 容器 + 若干 XML。用**系统自带** `java.util.zip` 解包 +
  系统自带 XML 解析器读 `xl/sheet1.xml` 与 `xl/sharedStrings.xml`
- 体积增加 ≈ 0（不引入任何库）
- **绝对禁止引入 Apache POI**：10MB+ JVM 库，Android 上既超体积又跑不动
- 微信/支付宝的 xlsx 前面有若干行说明文字，**表头在中间**，解析器必须能自行定位表头行
  （现有 CsvIo 已有"按表头名定位列"的逻辑，可复用）
- 两家的表头不同 → 需要识别来源（按表头特征判定），解析规则同样外置 JSON

### 电子表格类导出物通用陷阱（写入 skill 候选）
- 千分位逗号 `1,299.00`
- 表头前有说明行
- 列顺序不固定 → 必须按表头名定位，不能按列号
- 编码：csv 可能是 GBK；xlsx 内部是 UTF-8

## 向用户交付的「总体概念」（六项）
1. 体积：APK 1.5~2.5 MB（androidx 四库占大头）；砍掉 appcompat 可到 0.6~1.0 MB
   数据：单条 200~350 字节（密文以 BLOB 存，勿 Base64，否则多膨胀 33%）；1 万笔 2~4 MB
2. 安装要求：Android 8.0+ / arm64-v8a / 侧载需临时开未知来源 / 需自备签名密钥（丢失则无法覆盖升级）
3. 对手机影响：通知监听几乎不耗电、不占通知栏；无障碍明显耗电且微信可能风控；
   国产 ROM 需加省电白名单；**通知使用权是全量的**（系统不给按 App 过滤），
   唯一对冲是零 INTERNET
4. 历史导入：微信服务号通道摩擦最低（待用户验证能否保存到手机文件夹）；
   邮箱通道现实做法 = 电脑解压 → 微信「文件传输助手」→ 手机
5. 权限：通知使用权 + 无障碍（可选）+ POST_NOTIFICATIONS + RECEIVE_BOOT_COMPLETED；
   SAF 读文件不需权限；不声明 INTERNET
6. 运行依赖：Kotlin 标准库 + androidx 四库 + 系统自带 SQLite/Keystore/util.zip；
   无网络库、无统计、无 AI、无 native .so

### 仍未确认
