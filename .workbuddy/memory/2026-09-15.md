# 2026-09-15

## 调研：GitHub 上是否有可复用的开源底子

用户提问「github 上面有什么好的方案，或者适配这个需求部分，我只需要在他的基础上修改」。
用 GitHub API 跑了 6 轮检索 + 源码核实，脚本落在 `.workbuddy/gh_search*.py` / `gh_probe*.py` / `gh_fetch.py`。

### 核心结论：没有能直接 fork 的成品，但有可抄的零件

**不能 fork 成熟记账 App 的原因**：你的三个硬约束（绝对离线 / 极小体积 / 零第三方依赖）
把所有成熟项目排除在外——
- `mtotschnig/MyExpenses` ★1180 GPL-3.0 活跃，但 repo 320MB、Room 架构，砍到 2MB 比重写还费
- `Ivy-Apps/ivy-wallet` ★3175 GPL-3.0 **已归档**（2026-04 停止维护），Compose + Room

### 最重要的发现：AutoAccounting ★911
- `AutoAccountingOrg/AutoAccounting` Kotlin GPL-3.0，**活跃维护到 2026-09-14**，主页 ez-book.org
- 这是「自动抓取支付宝/微信账单」赛道最主流的开源项目，**验证了这条技术路线真实成立**
- **但不能直接用**，三个原因：
  1. **它是采集插件不是账本**——本身不记账，要把账单喂给钱迹/一羽/一木/小星等
     **联网的商业记账 App** → 直接破坏绝对离线
  2. 完整功能要 Root + LSPosed；无 Root 只能退到 OCR 模式（无障碍/Shizuku）
  3. **它自己联网**：代码含 `http/api/BillAPI.kt`、`RuleAPI.kt`、`update/RuleUpdateHelper.kt`、AI 辅助模块
- 组织下另有 `AutoRuleSubmit`（MIT，规则经由 GitHub Issue 提交）、`QianjiProvider`、`RapidOcrAndroidOnnx`

### 可直接借鉴的零件（按价值排序）

1. **`deb-sig/double-entry-generator`** ★719 Go Apache-2.0 活跃 —— 最高价值
   - 支付宝字段：交易时间 / 交易分类 / 交易对方 / 商品说明 / 收支出 / 金额 /
     收付款方式 / 交易状态 / 交易订单号 / 商家订单号；收支枚举 `支出/收入/不计收支`
   - 微信字段：交易号 / 商家订单号 / 付款时间 / 收支出 / 交易对方 / 商品名称 / 金额 /
     交易类型 / 交易状态 / 支付方式 / 服务费；**中性交易用 `/` 表示**
   - 微信交易类型枚举：商户消费、微信红包、转账、二维码收款、扫二维码付款、群收款、退款、转入零钱通-来自零钱
   - 注：它是 CSV 时代产物，但**表头名与 xlsx 一致**，可直接进 parser_rules.json

2. **`DykiSensei/seamless-bookkeeping`** ★5 Kotlin MIT —— 架构与本项目几乎同构
   - `notification/` 含 NotificationParser / CategoryClassifier / KeepAliveService /
     NotificationListenerHelper / SmsParser；`notification/accessibility/` 含
     AccessibilityCaptureService / AccessibilityExtractor / AccessibilityNodeUtils
   - **NotificationParser.kt 注释里有 6 条真实通知样本**（调研自 v2ex / AutoAccountingOrg issues）
   - **两条实测局限（修正我此前的估计）**：
     a. **微信扫码收款 2020 年后不再发系统通知** → 收款方向覆盖率比估计更低
     b. **支付宝转账入账通知不含金额**（"某某给你转了一笔钱，点击查看详细信息"）→ 必须丢弃
   - 正则技巧：`向\s*(?!你|您)(\S+?)\s*付款` 用负向断言排除"向你付款"（值得吸收）
   - **它的金额正则同样漏千分位** —— 我修过的 `[0-9][0-9,]*` 比它更严

3. **`FridayKoi/WhereIsMyMoney`** ★3 Apache-2.0 —— 有 `util/XLSXParser.kt`
   - 表头定位逻辑可参考（找含"交易时间"的行 + 列名 fallback 匹配 `findColumn("交易对方","对方")`）
   - **但内部就是 Apache POI**（`org.apache.poi.ss.usermodel.WorkbookFactory`），不是轻量方案，
     只能抄逻辑不能抄实现

4. **`MickLife/KeepAccounts_v2.0`** ★311 单文件 Python —— 微信支付宝账单合并清洗逻辑，可对照

### xlsx 读取的现成方案评估
- `dhatim/fastexcel` ★914 Java —— 依赖未核实通过，且违反零依赖约束
- `centic9/poi-on-android` ★402 Apache-2.0 —— 唯一成熟的 Android 上跑 POI 的路径，
  但 POI 本体 10MB+，与体积目标冲突（仅在放弃体积约束时可考虑）
- `youichi-uda/droidxls` ★2 —— 声称轻量，未验证，不可依赖
- **结论：xlsx 读取自己写**（系统 zip + 流式 XML，约 300 行）

### 协议风险
- GPL-3.0（MyExpenses / Ivy Wallet / **AutoAccounting**）：自用无碍，但代码抄进自己的项目再分发有传染性
- Apache-2.0 / MIT（double-entry-generator / seamless-bookkeeping / WhereIsMyMoney）：可自由借鉴
- 结论：**自用侧载下 GPL 不构成障碍；若日后开源，只抄 MIT/Apache 的**

### 采纳的策略（混合，不 fork）
保留自己的骨架 + 从 double-entry-generator 抄列名映射与枚举 + 从 seamless-bookkeeping
抄真实通知样本与正则技巧 → 全部落进 `parser_rules.json` 与其测试用例；xlsx 读取自研。

## 方案修订 v1.1：放宽「绝对离线」为「数据永不出户 + 可选受控联网」

用户澄清：不联网的真实诉求是**怕数据被偷偷上传**，不是物理断网，可适当放宽。

核心设计（已落入 `docs/方案设计.md` v1.1）：
- **双构建版本（productFlavors）**：`offline` 版零 INTERNET（物理保证保留）；
  `plus` 版声明 INTERNET，唯一用途是规则单向下载。同签名可互切、数据不丢
- **规则在线更新**（借鉴 AutoAccounting 的 RuleUpdateHelper/AutoRuleSubmit 模式，
  但砍掉自动后台更新）：手动触发 → 域名白名单（raw.githubusercontent.com/gitee.com）
  → SHA-256 校验 → 沙盒跑样本验证 → 原子替换。五道闸门任一失败保留原规则
- **网络代码收敛**：全部在 `net/RuleUpdater.kt` 单文件（系统 HttpURLConnection，
  零新依赖，不引 OkHttp/Retrofit）；只 GET 无 POST、无设备标识、无遥测
- **验证拆分**：offline 版跑 `verify_offline.sh`；plus 版新增
  `tools/verify_network_safety.py`（网络调用点仅存在于 RuleUpdater + 权限核对）
- 路线图插入 P3（规则在线更新），原 P3 顺延为 P4；P0~P2 不受联网决策影响
- 依然禁止：云同步、云备份、第三方 SDK、统计/崩溃上报——这些才是数据外泄的真正通道
- 初始规则包内容来源 = 开源调研成果（double-entry-generator 映射 + seamless-bookkeeping 样本）

## 方案 v1.1 第一性原理审计（用户指令：只审查，不修改）

结论：架构方向正确、工程可行；需求三要素中「本地」完全匹配，「自动」70-80% 有天花板（外因），
「准确归类」有条件匹配。**发现一个 P0 级设计缺口**：

1. **去重指纹在"通知缺商户名"场景失效 → 双记账**（§4.3）
   - 指纹 = 金额 hash + 商户 hash + 方向 + ±3min；通知记录商户为空/「未识别商户」，
     xlsx 记录商户为真名 → hash 对不上 → 同一笔交易插两次
   - 修正方向：xlsx 导入对既有通知记录做**合并回填**（金额+方向+±3min 匹配 →
     回填商户名/交易单号/官方分类），而非仅判重丢弃。回填同时是归类准确率的主要来源
2. M0 里程碑缺失：42 文件骨架从未编译过，任何新代码前先「编译通过+现有单测全绿」
3. 「准确归类」无可量化验收指标（建议：导入后未分类占比、月度手动修正次数趋势）
4. 覆盖率可见性缺失：首页应显示「最近导入时间」，否则用户忘了导入账目长期残缺
5. 备份导出排 P4 偏晚：修正记忆是数月积累资产，丢失成本高，建议提前到 P2 后
6. 支付宝 xlsx 自带「交易分类」列（微信的「交易类型」不是分类，已正确处理），
   可作初始分类种子，方案只把它当"辅助信号"，低估了
7. 范围纪律：P3/P4（规则在线更新等）冻结，直到 P0-P2 真机验证通过
粗估工作量：M0 半天；P0 2-4 晚；P1 2-3 晚+真机调试；P2 1-2 晚

以上 7 条已向用户汇报，**等拍板后再改方案文档**。
